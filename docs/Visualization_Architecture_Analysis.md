### 1.2 기존 공통화 수준 **[확인]**

핸드오프 §9는 "기존 공통 컴포넌트 위치"를 미확인으로 뒀는데, 실제로는 **이미 상당히 공통화돼
있다.** 새로 만들 것보다 이미 있는 것을 정리할 여지가 크다.

1. **차트 래퍼가 이미 있다** — `shared/chart.tsx`. 소비자가 1곳뿐이라 "공통화 대상"이라기보다
   _아직 두 번째 사용처가 없는_ 상태다.
2. **Canvas 토큰 해석기가 이미 있다** — `packages/features/src/knowledge-graph/model/node-colors.ts`.
   Canvas는 `var()`를 못 읽으므로 `getComputedStyle(document.documentElement)`로 토큰 값을 읽고
   캐싱한다. 내가 CLAUDE.md §5에 "새로 만들자"고 적은 resolver가 **이미 존재한다.**
3. **시각화 전용 토큰 계약과 그 강제 장치가 이미 있다** — 같은 파일의
   `KNOWLEDGE_GRAPH_COLOR_TOKENS` 14개와, 이를 검증하는 **앱별 테스트**
   `apps/spire/src/app/knowledge-graph-tokens.test.ts`, `apps/axflow/src/app/knowledge-graph-tokens.test.ts`.
   토큰 값은 각 앱 `styles.css`에 있고 **의미 토큰의 별칭**으로 정의된다
   (`apps/spire/src/styles.css:243` → `--color-kg-node-issue: var(--color-status-error);`).

> 앞선 세션에서 내가 "AxFlow에 데이터 색상 토큰이 `--color-data-1/2` 둘뿐이라 다계열 차트가
> 불가능하다"고 보고했다. 차트 쪽은 여전히 그렇지만, **그래프 쪽은 전용 토큰 패밀리와 강제
> 테스트까지 이미 만들어져 있다.** 따라서 시리즈 토큰이 필요할 때 새 메커니즘을 제안할 게 아니라
> `--color-kg-*` 선례를 그대로 따르면 된다.

## 3. 설계안 — 최소 계약

핸드오프 §7의 계층 모델을 현재 코드에 대입한 결과다. **폴더명·패키지명은 확정하지 않는다.**

```
업무 화면(route)        → 조회·필터·라우팅.        이미 이렇게 되어 있음(monitoring)
업무별 변환(lib)        → API 응답 → 표현 입력.    이미 분리돼 있음(monitoring/lib/data.ts)
공통 표현(ui)           → props만 받음.            TokenUsageChart가 이미 이 형태
공통 렌더링 primitives  → Canvas 그리기·히트·토큰.  ← C1/C2/C3가 만들 계층
내부 렌더링 구현        → recharts / force-graph.   교체 가능성은 열어두되 지금은 유지
```

**계약은 두 개로 나눠 유지한다.** 핸드오프 §7이 명시한 대로 하나로 합치지 않는다.

- 시계열·카테고리: `{ points, series, unit }` — recharts가 이미 받는 형태에서 출발
- 관계 그래프: `{ nodes, edges }` — `packages/core`의 `knowledge-graph` 타입에서 출발

**이벤트 계약도 최소로 시작한다.** 현재 두 화면이 실제로 발생시키는 것만 —
노드 선택, 노드 호버, 빈 영역 클릭. 그 외는 요구가 생길 때 추가한다.

**S5까지 마친 뒤에야** 이 저장소의 코어가 제품에 들어갈 자격이 있는지 판단할 근거가 생긴다.

> 주의: 이 저장소의 `Canvas2DBase`(약 390줄)는 **범용 pan/zoom/hit 캔버스**이고, AxFlow의
> `GraphCanvas`는 **force 시뮬레이션이 좌표를 밀어 넣는 캔버스**다. `react-force-graph`가
> `nodeCanvasObject` 콜백으로 렌더링 주도권을 쥐므로, `Canvas2DBase`가 그대로 대체하려면
> force 레이아웃을 분리해 직접 구동해야 한다. **이건 단계3(자체 구현)이지 단계1이 아니다.**

## 5. 자체 구현 검토 항목

핸드오프 §8의 다섯 질문에 현재 근거로 답할 수 있는지 확인했다.

| 질문                       | 현재 답                                                                                                                                                         |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 무엇이 실제로 막히는가?    | **근거 없음.** 구현 불가능한 UX나 측정된 병목이 코드·문서에 기록돼 있지 않다                                                                                    |
| 지금 도구로 해결 가능한가? | `GroundsGraph.tsx:17`, `GraphCanvas.tsx:47`이 이미 `lazy(() => import('react-force-graph-2d'))`로 코드 스플리팅을 적용해 두었다. 최적화 여지가 남아 있다는 신호 |
| 범위가 명확한가?           | 아니오. 대체 대상이 force 시뮬레이션인지, Canvas 렌더링인지, 둘 다인지 미정                                                                                     |
| 개선을 어떻게 증명하는가?  | 비교 기준 없음                                                                                                                                                  |
| 유지 가능한가?             | 미판단                                                                                                                                                          |

**결론: 현재 코드 근거만으로는 자체 구현 전환의 필요성을 판단할 수 없다.**

특히 **ECharts 도입도 같은 기준에 걸린다.** ECharts는 AxFlow에 0건이므로 도입은
"기존 라이브러리 활용"이 아니라 **세 번째 렌더링 엔진 추가**다. recharts 소비자가 1곳인 현재
상태에서 두 번째 차트 엔진을 넣을 근거가 코드에 없다. 이 저장소가 ECharts 기반으로 만들어져
있다는 사실은 *이 저장소의 사정*이지 제품의 근거가 아니다.
